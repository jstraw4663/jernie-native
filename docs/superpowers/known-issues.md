# Known Issues / Backlog

Findings discovered during development that are real but out of scope for the pass that found them. Logged here so they don't get lost to conversation context. Add to this list as new deferred findings come up; remove entries once actually fixed (reference the fixing commit/PR).

## Security / correctness

- **Group-scoped visibility (`groupIds`) is enforced only client-side.** `src/domain/groups.ts`'s `filterVisibleToUser` is correctly built and centralized, but nothing in `database.rules.json` restricts *reads* by group membership — any trip member's client (or anyone hitting the RTDB REST API directly with that member's token) can read every other sub-party's group-scoped bookings/itinerary items in full. `groupIds` currently only controls what renders, not what's transmitted. Found during the post-data-model-foundation `/simplify` pass (2026-07-13).
- **No `.validate` rules on trip content collections.** `stops`/`bookings`/`itinerary`/`confirms`/`reservationTimes`/`places` in `database.rules.json` have no shape validation — only `members`/`joinProofs`/`inviteTokens` got it during the data-model-foundation work. Since no Cloud Functions are deployed, RTDB rules are the only server-side backstop today; any authenticated trip member can currently write arbitrary garbage into another member's data. Found during the `/simplify` pass (2026-07-13).

- **No way to remove a member from a trip.** Membership is write-once by rule (`members/$uid` requires `!data.exists()`) and nothing in the UI removes one. This becomes visible in the Phase 1 beta: invites stay open to anonymous users, so a traveller who joins anonymously and then loses their device is a permanent ghost in the organizer's member list — unreachable and unremovable. Accepted deliberately when scoping Phase 1 auth (2026-08-20); gating the join side was rejected because it demands sign-in from someone who just tapped a friend's link. Needs a removal path (and a rules change to allow the organizer to delete a member record) before public launch.

## Architecture

- **Rental cross-stop linking is rental-specific; should generalize.** `RentalBooking.dropoffStopId` (and the "Pickup here"/"Drop-off here" badge logic in `TravelCard.tsx`) models a booking that spans two stops, but it's hardcoded to rentals. Other booking types or future features may need the same "spans multiple stops" concept. Current behavior is correct, just narrowly named/scoped. Raised by the user during Explore-tab planning (2026-07-13) — logged for a later pass rather than done immediately.
- **Most curated `Place` records have no coordinates yet.** `Place.lat`/`Place.lon` are only populated where the one-time enrichment import (`scripts/importFirestoreEnrichment.ts`) backfilled them — most places (and everything added by future manual curation, until this is addressed) will lack coordinates, meaning `getPlaceEnrichment()` can never look up cached enrichment for them (fails closed — no crash, just no enrichment shown, section hidden). Any future curation UI or auto-seed flow should always capture lat/lon per place. Found while building the canonical-key enrichment cache (2026-07-14).
- **`useFirestoreEnrichment` does one Firestore `.doc().get()` per place with coordinates, no batching.** Fine at current scale (tens of places per trip). If a trip's place count grows very large, switch to chunked `where(documentId(), 'in', ...)` queries (30 per chunk) or reconsider the access pattern. Found while building the canonical-key enrichment cache (2026-07-14).
- **"Suggest places near my stops" is a separate future feature, not this cache.** The global `place_enrichment` collection is a lookup cache for places *already selected* into a trip — it should never be queried by radius/proximity, and isn't a substitute for a real nearby-places search. A future auto-seed feature (`seedExploreTab` in the original migration spec) should call Foursquare's/Google's own live nearby-search API directly to discover candidate places for a new trip's stops, then consult this cache only to avoid re-fetching detail data for places it's already seen. Clarified with the user while designing the canonical-key scheme (2026-07-14).
